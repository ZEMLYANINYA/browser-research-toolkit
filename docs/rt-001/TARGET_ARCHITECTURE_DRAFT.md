## 1. Проверка гипотезы против того, что реально есть в коде

### 1.1 Sensors — гипотеза подтверждается структурно, но покрытие неполное (пересмотрено в corrective pass)

**FACT.** `src/interceptors/*` (6 файлов) + `src/monitors/*` (7 файлов) уже являются
сенсорами в чистом виде: каждый реализует `install()`/`restore()` или `install()`/`teardown()`
(`src/types.ts:226-235`), не знает о существовании других сенсоров, получает всё через `ctx`
(`CollectorContext`). Композиция происходит только в `collector.ts`. Это уже ровно то разделение,
которое предлагает гипотеза — переименовывать/перестраивать нечего, слой **уже существует и
работает**.

**INFERENCE.** Legacy (и generic, и все 8 site-specific, и оба antibot-файла) не имеют этого
разделения вообще — весь functionality одного файла живёт в одном классе на ~30-40 методов.
Переход к слою "sensors" — это то, что **уже произошло** при переписывании на TypeScript,
не то, что предстоит сделать.

**Уточнение (corrective pass — независимый review справедливо указал, что формулировка "гипотеза
подтверждается" была слишком сильной).** Структурное разделение (независимые install/teardown-модули)
— готово. Но **покрытие** Sensors-слоя — нет, пять конкретных пробелов, каждый подтверждён кодом:

1. **Timer sensor отсутствует.** Нигде в `src/` `setTimeout`/`setInterval` не патчатся как источник
   наблюдения (grep `setTimeout\s*=|setInterval\s*=` — 0 совпадений; единственный `setTimeout` в
   `collector.ts:78` — собственный служебный вызов коллектора, не сенсор).
2. **Initiator/stack-based sensor для сетевых запросов отсутствует.** Стек захватывается только для
   `ErrorEntry` (`logger.ts:56`), никогда — для обычного запроса. Единственное поле с "initiator" в
   имени (`performance-monitor.ts:49`, `initiatorType`) — нативный браузерный тег типа ресурса
   (`'fetch'`/`'script'`), не код-локация инициатора.
3. **Навигация — только сырая пара URL, без семантики, и с реальным дефектом.**
   `NavigationRecord{type, from, to, timestamp}` (`types.ts:155-160`) не различает
   пользовательский back/forward от программной смены маршрута, не привязывается к route/компоненту.
   Хуже: обработчик `popstate` (`navigation-monitor.ts:15-18`) передаёт `window.location.href` и как
   `from`, и как `to` — оба значения синхронно идентичны — а `record()` (строка 54) содержит
   `if (from === to) return`, который поэтому отбрасывает **каждое** popstate-событие безусловно.
   Браузерная навигация назад/вперёд физически не долетает до `navigationHistory`. Ни один тест
   этого не покрывает.
4. **Формального session-lifecycle sensor нет.** Ни `visibilitychange`, ни `pagehide` не
   прослушиваются нигде (grep — 0 совпадений); нет multi-tab/multi-instance awareness; единственный
   lifecycle-примитив — плоский булев `ctx.isActive`, переключаемый `start()`/`stop()`.
5. **Кросс-сенсорных связей на момент захвата нет.** Ни один interceptor не читает данные,
   записанные monitor'ом, и наоборот, за пределами общей инфраструктуры `ctx` (sanitizer, logger,
   isActive, config) — каждый модуль пишет только в свой собственный срез состояния.

**Уточнённый вывод.** Правильная формулировка — "current toolkit имеет сильную структурную основу
Sensors-слоя (сеть + DOM + storage + performance + базовая навигация), но **не покрывает его
полностью**" — а не безусловное "гипотеза подтверждается". См. также новый §1.7 ниже
(Session/Lifecycle Boundary Integrity) — отдельный, смежный класс пробелов в том же слое.

### 1.2 Unified Event Model — гипотеза НЕ подтверждается, и это важно

**FACT.** В `src/types.ts` нет единой Event-модели. Есть восемь **структурно разных**,
непересекающихся типов данных, каждый со своей формой и своим хранилищем в `CollectorContext`:
`RequestData` (→ `networkRequests`/`endpoints`), `WebSocketData` (→ `websockets`), `EventRecord`
(→ `events: Map<string, BoundedList<EventRecord>>`, ключ — тип DOM-события), `BeaconRecord`
(→ `beacons`), `EventSourceRecord` (→ `eventSources`), `DomResourceRecord` (→ `dynamicResources`),
`NavigationRecord` (→ `navigationHistory`), `MutationDiscoveryRecord` (→ `mutationDiscoveries`),
`StorageEntry` (→ `localStorageMap`/`sessionStorageMap`/`cookies`), `PerformanceEntryData`
(→ `performanceData`), `ErrorEntry` (→ `logger.errors`).

У всех есть `timestamp`, но не более того — нет общего дискриминированного union'а, нет общего
`type`+`payload` конверта, нет единой точки, через которую можно было бы итерироваться "по всем
событиям сессии независимо от их природы".

**FACT.** Legacy (весь, включая generic) устроен так же — отдельные `Map`/массивы на каждый тип
данных, без единой модели.

**INFERENCE.** Отсутствие Unified Event Model **не помешало** ни одной из реально работающих
correlation-примитивов, обнаруженных в `CORRELATION_GROUNDWORK.md`:
- request↔response корреляция работает через общий JS-объект, разделяемый между interceptor и
  analyzer (не через общую схему событий).
- `findClosestASIN` (единственная рабочая user-action→entity связь) работает через DOM-обход, не
  через событийную модель вообще.
- response→created-entity enrichment (`createdPostId`/`createdTweetId`) работает через ту же
  общую ссылку на объект запроса.

Единственная связь, которая **не** реализована ни в одном файле репозитория — `domTrigger`/
`lastInteraction` (user action → request по времени) — не реализована не потому, что не было общей
событийной модели, а потому что **не было общего "последнего взаимодействия" указателя,
обновляемого DOM-слушателем и читаемого интерсепторами**. Это узкая, аддитивная фича (один
разделяемый mutable-указатель + один capture-фазный listener), не требующая переписывания всех
восьми существующих типов данных в единую схему.

**Вывод RT-001 (первая версия).** Гипотеза "Unified Event Model — необходимый фундамент для
Correlation" не подтверждается имеющимися свидетельствами как требующая немедленной полной
реализации. Наблюдаемая потребность (связать действие с запросом) технически закрывается точечным
дополнением к существующей архитектуре, без замены восьми типов данных на одну модель.

**Пересмотр в corrective pass.** Независимый review указал, что вывод "поэтому реализуем
`lastInteraction` в production как следующий шаг" был **слишком быстрым** — он смешивал два разных
вопроса: (а) нужен ли *прямо сейчас* full UEM-рефакторинг (ответ по-прежнему НЕТ, аргументация ниже
не изменилась) и (б) следует ли *из этого* делать вывод, что можно сразу писать production-примитив
корреляции, минуя валидацию (ответ ДОЛЖЕН БЫТЬ НЕТ — это отдельный вопрос, не следующий
автоматически из (а)). Дополнительно, находки этого corrective pass (`CORRELATION_GROUNDWORK.md`
§10 "Temporal Semantics", §11 "Session/Lifecycle Boundary Integrity") добавили конкретные новые
аргументы, которых не было в первой версии:

- В `src/` нет монотонного sequence-номера кросс-типовых событий, нет `performance.now()`, нет
  session ID — три примитива, которые продемонстрированно (не гипотетически) не позволяют
  восстановить причинный порядок при столкновении меток `Date.now()` (конкретный сценарий: клик,
  синхронно вызывающий `fetch()`, — обе записи могут получить идентичный timestamp).
- Session/Lifecycle Boundary Integrity (§1.7 ниже) означает, что "принадлежность записи текущей
  сессии" сама по себе сейчас не гарантирована — WS-сообщение может физически прийти и записаться
  после логического конца сессии.

Оба этих факта — не про то, нужен ли **полный** UEM, а про то, что **даже точечному** correlation-
примитиву (`lastInteraction` или любому другому) для надёжной работы нужна какая-то форма
временной/причинной инфраструктуры, которой сейчас нет вообще ни в каком виде — ни полной (UEM), ни
минимальной.

**PROPOSAL — введение промежуточной гипотезы: MINIMAL TEMPORAL / CORRELATION ENVELOPE.**
Между "ничего не менять в модели данных" и "переписать все 8 типов в один Unified Event Model" есть
третий, не рассмотренный в первой версии документа вариант: не заменять существующие типы данных, а
**добавить к ним общий, тонкий "конверт"** — не переписывающий структуру самих `RequestData`/
`EventRecord`/`NavigationRecord`/etc., а прикладываемый к ним при записи. Кандидатный состав полей
(гипотеза, не финальная схема):

| Поле | Назначение |
|---|---|
| `sessionId` | Отличает записи одного запуска коллектора от другого — сейчас нет вообще (см. `CORRELATION_GROUNDWORK.md` §10) |
| `eventId` | Уникальный ID **любой** записи, не только запроса (сейчас `generateId()` — только для запросов) |
| `source`/`kind` | Какой сенсор произвёл запись (interceptor/monitor и тип) — сейчас определяется только по тому, в какой коллекции лежит запись |
| `timestamp` (wall-clock) | Уже есть везде — `Date.now()`, без изменений |
| `monotonic` | `performance.now()` — решает проблему коллизии меток при одинаковом `Date.now()` (см. `CORRELATION_GROUNDWORK.md` §10) |
| `sequence` | Монотонный счётчик, инкрементируемый при **любой** записи любого типа — решает ту же проблему проще, без зависимости от точности таймера |
| `sanitizedPayload` | То, что сейчас и так пишется в каждую структуру — редактированные данные |
| `parentId`/`relatedIds` | Место для будущих находок Correlation Engine (например: `RequestData.parentId = <eventId клика>`), не обязательно заполняется сразу |
| `confidence` | Для эвристических связей (например response→created-entity, см. `CORRELATION_GROUNDWORK.md` §5) — числовая уверенность, а не бинарный факт |
| `ruleVersion` | Версия правила, которое установило связь — чтобы можно было переисполнить/пересчитать корреляции при изменении эвристики без потери сырых данных |

**Ключевое архитектурное отличие от полного UEM.** Этот конверт **не требует** заменять
`RequestData`/`EventRecord`/`NavigationRecord`/... одним дискриминированным union'ом и не требует
менять существующие `BoundedStore`/`BoundedList`-коллекции в `CollectorContext`. Он может быть
реализован как **sidecar timeline/projection** — отдельная, дополнительная тонкая коллекция
(`{eventId, sessionId, sequence, monotonic, source, timestamp} → ссылка на исходную запись`),
строящаяся **поверх** существующих хранилищ, а не вместо них. Практически: каждый interceptor/
monitor при записи в свою существующую коллекцию **дополнительно** регистрирует конверт в общем
sidecar-индексе. Это аддитивно (не трогает существующие типы/тесты/экспорт), но даёт Correlation
Engine то, чего сейчас нет ни в каком виде: единую, кросс-типовую, монотонно упорядоченную временную
линию для итерации, без переписывания восьми типов данных.

**Разграничение (явно, чтобы не повторить ошибку первой версии документа).**

- **FULL UEM** = заменить существующие 8 типов одной моделью. По-прежнему **не рекомендуется** как
  первый шаг — тот же аргумент blast radius, что и в первой версии (см. ниже).
- **MINIMAL TEMPORAL ENVELOPE** = добавить тонкий sidecar-слой поверх существующих типов, ничего не
  заменяя. Не рекомендуется реализовывать *немедленно* — это тоже гипотеза, а не решённый вопрос —
  но рекомендуется **оценить** (не реализовать) как отдельный шаг **до**, а не вместо валидации
  самой correlation-гипотезы (см. §5 и `MIGRATION_PLAN.md`).

**Вывод про сам полный UEM (не изменился относительно первой версии).** Вводить его **как первый
шаг** значило бы переписать 8 из 8 существующих типов данных и все модули, которые их создают/читают
(`context.ts`, все interceptors, все monitors, `collector.ts`, `export/exporter.ts`) ради выгоды,
которая пока не доказана более чем одним сценарием использования. Это прямо противоречит принципу
§16 задания "предпочитай маленькие проверяемые изменения". UEM остаётся оправданной инвестицией
только тогда, когда появится больше одного реального потребителя, которому нужна единообразная
итерация по всем типам событий.

### 1.3 Profiles — гипотеза подтверждается, но с уточнением: контент есть только в legacy

**FACT.** `src/` не содержит ни одного profile/классификатора — `ctx.isApiEndpoint()`
(`context.ts:96-100`) — единственная "классификация", и она keyword-based, без доменной семантики
(product/post/tweet/pin и т.д. отсутствуют полностью — см. `INVENTORY_MATRIX.md`, APPLICATION
SEMANTICS).

**FACT.** Весь материал для будущего "profile" слоя существует только в `legacy/site-specific/*`
(URL/GraphQL-operation → доменная категория → entity ID extraction → DOM-селекторы) — разобрано
детально в `LEGACY_FINDINGS.md` §2.

**INFERENCE.** Гипотеза верна структурно (profile-слой как отдельная, подключаемая единица — разумное
разделение), но нужно явно зафиксировать: **ни одна конкретная профильная реализация из §7 задания
(`profiles/generic`, `profiles/graphql`, `profiles/antibot-observability`) сейчас не существует ни
в каком виде** — это чистый PROPOSAL, вдохновлённый паттерном, многократно замеченным в legacy
(классификатор URL/body → бакет → extractor полей), но не готовый код и не готовая схема.

### 1.4 Correlation — гипотеза подтверждается направлением, но не готовностью

**FACT.** Ни в `src/`, ни в каком-либо legacy-файле нет отдельного Correlation-модуля.

**INFERENCE (из `CORRELATION_GROUNDWORK.md`).** Реальных, работающих correlation-примитивов в
репозитории — три с половиной (request↔response, ancestor-DOM resolution, response→entity
enrichment, плюс намерение domTrigger). Это достаточно материала, чтобы понимать **форму** первой
версии Correlation-слоя (см. `MIGRATION_PLAN.md`), но недостаточно, чтобы уже сейчас проектировать
общий движок с произвольными правилами — большинство связей из §13 задания (navigation→network,
timer→network, request→DOM change) не имеют вообще никакого прецедента в коде, ни рабочего, ни
сломанного.

### 1.5 Inference — гипотеза почти не подтверждается фактическим материалом

**FACT.** Единственный код во всём репозитории, который делает что-то похожее на "inference"
(в терминах §5 задания — "обнаружить повторяющийся механизм"), — это `AntiBotAnalyzer.isSuspicious()`
(`ANTIBOT_ANALIZ.js:30-38`) — плоская проверка вхождения keyword'а в сериализованный JSON лога, и
`RedditGraphQL`/`X_COM` response-derived entity enrichment (см. §1.4) — но это скорее "ре-запись
факта", чем "вывод по нескольким наблюдениям".

**INFERENCE.** Пример из §5 задания ("Load More → SearchProducts → offset изменился → 24 сущности →
24 DOM-узла → вероятно pagination") не имеет **никакого** прецедента в текущем коде — ни рабочего,
ни сломанного, ни даже объявленного как namespace/поле состояния (в отличие от `domTrigger`, которое
хотя бы было заявлено). Это самый "PROPOSAL"-слой из всех шести — здесь буквально не на что
опереться, кроме самой гипотезы. Планировать Inference раньше, чем заработает Correlation, было бы
преждевременным — INFER логически потребляет выход CORRELATE.

### 1.6 Presentation / Export — гипотеза частично подтверждается, но с конфликтом philosophy

**FACT.** `src/export/exporter.ts` — единственная реализация экспорта во всём репозитории (весь
legacy site-specific экспорта не имеет вообще, только `window.get*`-команды для live-инспекции,
см. `INVENTORY_MATRIX.md`/DATA MANAGEMENT). Формат — плоский JSON-дамп всех коллекций, без
нарратива, без "объяснения" в духе §5 задания.

**INFERENCE.** Есть архитектурное расхождение между тем, что уже есть (`src/` — batch JSON export),
и тем, чего было **больше** в legacy (live query API, `getSessionInfo()`/`getVoteHistory()`/
`getGraphQLQueries()` и т.д. — интерактивная инспекция работающей сессии). Будущий "Presentation"
слой, если он должен когда-либо произвести человекочитаемое EXPLAIN-повествование (пример из §5
задания), — это качественно другая задача, чем текущий JSON-экспорт, и ближе по духу к
`getSessionInfo()`-паттерну legacy (интерактивный запрос к живым данным), чем к batch-дампу.

### 1.7 Session / Lifecycle Boundary Integrity — новый архитектурный риск (corrective pass)

> Не входит в шестислойную гипотезу §6 задания напрямую, но обнаружен при верификации замечаний
> независимого review и признан достаточно важным, чтобы задокументировать отдельно — он влияет
> на надёжность любого будущего Correlation/Inference слоя.

**FACT.** `ResearchCollector.cleanup()`/`stop()` (`src/collector.ts`) не является атомарной границей
между "коллектор работает" и "коллектор остановлен". Конкретно:

1. **WebSocket/EventSource** (`websocket-interceptor.ts`, `eventsource-interceptor.ts`) — `restore()`
   меняет только глобальный конструктор (`window.WebSocket`/`window.EventSource`); слушатели
   `message`/`open`/`close`/`error`, уже привязанные напрямую к открытым на момент `cleanup()`
   соединениям, а также патченный `ws.send`, не имеют проверки `ctx.isActive` и продолжают писать в
   `ctx.websockets`/`ctx.eventSources` неограниченно долго после `cleanup()` — пока соединение не
   закроется само по инициативе страницы.
2. **fetch/XHR** (`fetch-interceptor.ts`, `xhr-interceptor.ts`) — `ctx.isActive` проверяется один
   раз, синхронно, в момент отправки запроса. Ответ на уже отправленный запрос анализируется и
   записывается в контекст (`ResponseAnalyzer.analyzeFetchResponse`/`analyzeXhrResponse`, включая
   безусловную регистрацию endpoint'а в `finally`-блоке) без повторной проверки активности.
3. **PerformanceObserver/MutationObserver** — `teardown()` в обоих корректно вызывает `disconnect()`,
   но сам колбэк наблюдателя не содержит собственной проверки `ctx.isActive` — защита от
   пост-teardown срабатывания целиком полагается на браузерный тайминг отключения, а не на код.
4. **`ErrorMonitor`** — единственный модуль с полностью корректным, "эталонным" teardown: снимает оба
   `window`-слушателя и восстанавливает `console.error` без остатка. Это доказывает, что проблема —
   не платформенное ограничение, а несогласованность между модулями, а не системная невозможность.
5. **`beforeunload`-слушатель** (`collector.ts:77`) регистрируется как анонимная inline-функция и
   никогда не снимается — при реальном закрытии страницы `cleanup()` вызовется повторно, даже если
   уже был вызван вручную. Для одного инстанса коллектора это безопасно (все `restore()`/`teardown()`
   идемпотентны, так как ни один interceptor не обнуляет своё сохранённое "original"-значение после
   использования) — но не гарантированно безопасно при нескольких инстансах (см. ниже).
6. **Несколько инстансов коллектора на одной странице** безопасны только при восстановлении в строго
   обратном порядку установки (LIFO): если инстанс A восстанавливается раньше инстанса B (не в LIFO-
   порядке), `window.fetch`/`XMLHttpRequest`/`WebSocket` в итоге останется указывать на "мёртвую"
   обёртку A вместо истинно нативной функции — молча, без ошибки. Восстановление в LIFO-порядке
   (последний установленный — первый восстановленный) работает корректно.

**INFERENCE.** Ни один из этих шести пунктов не является веткой одной общей причины — это
независимые проявления одного архитектурного решения: "остановка" реализована как "сигнал для новых
операций", а не как "гарантированный барьер для уже начатых". Для простого observability-инструмента
(сегодняшнее назначение toolkit) это приемлемый компромисс. Для будущего Correlation Engine, который
будет опираться на понятие "принадлежность записи к сессии", это уже не нейтральный компромисс —
запись, физически пришедшая после логического конца сессии, будет неотличима от записи, пришедшей
внутри неё, если только не ввести что-то вроде `sessionId`/`sequence` (см. §1.2 выше,
"Minimal Temporal Envelope").

**PROPOSAL (не реализовывать в RT-001).** Это самостоятельный, не связанный напрямую с
UEM/Correlation-дискуссией трек исправлений — см. `MIGRATION_PLAN.md`, отдельный ранний этап
"Lifecycle/Session Boundary Hardening". Рекомендуется решать его **раньше**, а не после начала
работы над correlation-примитивами, потому что доверие к границам "что относится к этой сессии" —
предпосылка для доверия к любой будущей корреляции, а не наоборот.

## 2. Итоговая оценка гипотезы

**PROPOSAL.** Шестислойное деление `Sensors / Unified Event Model / Profiles / Correlation /
Inference / Presentation` **в целом разумное направление**, но не одинаково готово по всем слоям:

| Слой | Готовность | Вывод |
|---|---|---|
| Sensors | Структурно реализовано в `src/` (независимые install/teardown-модули), но **покрытие неполное**: нет timer/initiator-сенсора, навигация без семантики (плюс сломан popstate), нет формального lifecycle-сенсора, нет кросс-сенсорного обмена (пересмотрено — §1.1) | Не требует новой архитектуры для того, что уже покрыто, но список конкретных пробелов — реальный, не гипотетический |
| Session/Lifecycle Boundary Integrity (не из исходной 6-слойной гипотезы, добавлено) | `cleanup()`/`stop()` — не атомарная граница (6 конкретных находок, §1.7) | Рекомендуется исправлять **раньше** correlation-работы, а не после |
| Unified Event Model (FULL) | Не существует; **по-прежнему не доказано, что нужен как первый шаг** | См. §1.2 — не рекомендуется как первый шаг |
| Minimal Temporal/Correlation Envelope (новая промежуточная гипотеза) | Не существует ни в каком виде — как и FULL UEM | См. §1.2 — не решённый вопрос, но кандидат для отдельной оценки, дешевле FULL UEM |
| Profiles | Не существует в коде; богатый материал есть только в legacy | Формализовать позже, начиная с декларативного, а не императивного формата (см. §3) |
| Correlation | Не существует; несколько реальных прецедентов из legacy задают форму (но не готовность к production — см. §3) | Требует сначала **валидации гипотезы** (post-hoc study), не сразу production-реализации |
| Inference | Почти нет материала для опоры | Рано проектировать; определять предметно после Correlation |
| Presentation/Export | Частично есть (batch JSON), но не в духе EXPLAIN | Нужно решить, батч или live-инспекция — не решать в RT-001 |

**PROPOSAL (структура директорий).** Гипотетическая структура из §6 задания (`core/{events,storage,
redaction,correlation,inference}`, `browser/*`, `profiles/*`, `presentation`) — разумный **дальний**
ориентир, но преждевременно фиксировать её как файловую структуру уже сейчас: `core/events` (=UEM)
и `core/inference` не имеют под собой готового содержания (см. §1.2, §1.5), а `browser/*` уже
существует под другими именами (`interceptors/`, `monitors/`) без явной причины их переименовывать
прямо сейчас. Рекомендуется вводить новые директории (`profiles/`, `correlation/`) по мере
появления в них реального кода, а не создавать пустые заготовки заранее.

## 3. Что подтверждено кодом как форма первого шага (для `MIGRATION_PLAN.md`)

Не проектируя реализацию здесь, но фиксируя, что именно подтверждено свидетельствами:

1. **"Last qualifying interaction" примитив — пересмотрено в corrective pass, НЕ рекомендуется
   сразу для production.** Ранее этот пункт рекомендовал прямую реализацию в горячем пути
   (`EventMonitor`/interceptors) как первый шаг. Независимый review справедливо указал, что это
   преждевременно — сила аргумента "8 файлов задумали эту связь" оказалась ниже, чем казалось (это
   1 скопированный шаблон, а не 8 независимых источников, см. `CORRELATION_GROUNDWORK.md` §3), и
   сама гипотеза "последнее взаимодействие → следующий запрос" никем и никогда не была
   эмпирически проверена — ни в legacy (там её только объявили, не реализовали), ни где-либо ещё.
   Явные, конкретные риски, которые нужно исследовать **до** production-реализации:
   - **Temporal coincidence** — запрос, случайно попавший в TTL-окно, но реально не связанный с
     кликом (фоновый polling/heartbeat, синхронизированный по времени с активностью пользователя
     случайно, не причинно).
   - **Background polling** — периодические запросы, не связанные ни с каким взаимодействием
     вообще, могут попасть в окно сразу после того, как пользователь кликнул на что-то другое.
   - **Analytics beacon** — аналитические/телеметрические запросы, срабатывающие на любое
     взаимодействие (включая нерелевантные для исследователя клики), создадут ложные срабатывания
     на каждый клик без исключения.
   - **Double-click** — второй клик в двойном клике может "перетереть" `lastInteraction`, ссылаясь
     на устаревшее взаимодействие к моменту, когда реальный запрос уйдёт.
   - **Click → submit** — клик по кнопке отправки формы порождает два квалифицирующих события
     (`click`, затем `submit`) для одного пользовательского намерения — неясно, какое из них должно
     "победить" как `lastInteraction`.
   - **Keyboard activation** — активация элемента клавиатурой (Enter/Space на фокусированной кнопке)
     не является кликом; если квалифицирующее множество событий этого не учитывает, часть реальных
     взаимодействий останется невидимой.
   - **Timer-delayed requests** — запрос, намеренно отложенный кодом страницы через `setTimeout`
     после клика (частый UX-паттерн debounce), может выйти за пределы разумного TTL и остаться
     несвязанным, либо, при слишком большом TTL, связаться с неверным более поздним кликом.
   - **Programmatic click** — `element.click()`, вызванный кодом страницы, не пользователем,
     неотличим от настоящего клика без дополнительной проверки.
   - **`event.isTrusted`** — единственный встроенный браузерный признак, отличающий пользовательский
     жест от программного (`Event.isTrusted`); в текущем `EventMonitor` не используется и не
     проверяется нигде — потенциально важный, но неисследованный сигнал.
   - **Overwriting previous interaction** — если между кликом и запросом происходит ещё одно
     квалифицирующее взаимодействие (например скролл, если он включён в множество), `lastInteraction`
     перезапишется до того, как исходный запрос уйдёт.
   - **TTL selection** — выбор порога (сотни мс? секунда?) не обоснован ничем, кроме интуиции; разные
     сайты/сценарии могут требовать разных значений.
   - **Privacy of DOM target** — описание DOM-цели взаимодействия (`target`, селектор/классы
     элемента) само по себе может быть чувствительным (например, кнопка с текстом, содержащим
     персональные данные) и должно проходить через `Sanitizer`, если реализовывать этот примитив —
     чего в исходном legacy-намерении не предусматривалось вообще.

   **Пересмотренная рекомендация:** прежде чем менять горячий путь `src/`, сначала проверить
   гипотезу **post-hoc**, на уже собираемых (без нового поля) DOM-событиях/запросах/навигации, на
   2-3 реальных SPA, с ручной разметкой causal ground truth и измерением precision/false positive
   rate — включая отдельную проверку каждого риска из списка выше. Детали процедуры — в
   `MIGRATION_PLAN.md`, этап "Post-hoc correlation study". Реализация в production — только если
   это исследование покажет приемлемую точность.
2. **Ancestor-based identity resolution** (`findClosestASIN`, `CORRELATION_GROUNDWORK.md` §4.1) —
   обобщается как "найти ближайшего DOM-предка с конфигурируемым атрибутом" — кандидат для
   будущего `profiles`-слоя (site-specific конфигурация атрибута) поверх generic-механизма обхода.
   **Уточнение:** сам файл-источник (`АМАЗОН.js`) сейчас не исполняется (SyntaxError, см.
   `LEGACY_FINDINGS.md` §2.1) — идея валидна, но не имеет текущего рабочего прецедента в этом
   репозитории; рабочий прецедент есть у структурно иного (closure-capture) механизма, см. п. 2а.
2a. **(Добавлено в corrective pass.) Closure-capture identity resolution** — реально исполняющийся
   (в отличие от п. 2) паттерн из 4 файлов (Reddit, X_COM, Pinterest, allegro,
   `CORRELATION_GROUNDWORK.md` §4.2): атрибут контейнера читается один раз при обнаружении через
   `MutationObserver`, замыкается в closure, используется при любом дочернем клике. Дешевле
   ancestor-walk (нет обхода DOM на каждый клик), но зависит от того, что контейнер не
   переиспользуется под другую сущность без повторного обнаружения.
3. **Классификатор запроса → доменная категория → extractor полей**, повторённый во всех 8
   site-specific файлах (`LEGACY_FINDINGS.md` §2) — материал для формата **декларативного**
   profile-описания (таблица правил, не код), но сам формат не спроектирован в RT-001.
4. **Memory-pressure backpressure** (`performance.memory.usedJSHeapSize`, обнаружено во всех 8
   site-specific файлах, отсутствует в `src/`) — не про Correlation, но реальный, многократно
   подтверждённый gap в `BoundedStore`, независимый от остальной архитектурной дискуссии.
5. **(Добавлено в corrective pass.) Response → created-entity extraction** (`CORRELATION_GROUNDWORK.md`
   §5) — реализовано в 2 из 8 файлов (Reddit, X_COM), но с подтверждённым риском false positive
   (не gated по типу операции create/view/like). Любая будущая реализация обязана проверять тип
   операции перед присвоением "создано".
