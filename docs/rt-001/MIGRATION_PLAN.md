## Этап 1 — Lifecycle / Session Boundary Hardening

**OBJECTIVE.** Устранить конкретные, подтверждённые кодом пробелы в границе `stop()`/`cleanup()`
(`TARGET_ARCHITECTURE_DRAFT.md` §1.7, "Session/Lifecycle Boundary Integrity"): WebSocket/EventSource
слушатели, не проверяющие активность после восстановления конструктора; fetch/XHR ответы,
дописываемые в контекст без повторной проверки активности; отсутствие задокументированного
LIFO-требования для восстановления нескольких инстансов коллектора.

**WHY NOW (первым, раньше correlation-работы).** Это не гипотеза и не эксперимент — это
подтверждённые дефекты в уже существующем, уже поддерживаемом коде, не зависящие от того, какое
архитектурное направление (UEM/minimal envelope/ничего) будет выбрано дальше. Более важно: любая
будущая работа с понятием "сессия" (а корреляция по определению строится вокруг него) будет
унаследовать эту нечёткую границу, если её не исправить сначала. Дешевле и безопаснее чинить это
до, чем поверх ещё не написанного correlation-кода.

**AFFECTED COMPONENTS.**
- `src/interceptors/websocket-interceptor.ts` — добавить проверку `ctx.isActive` в `message`/`send`.
- `src/interceptors/eventsource-interceptor.ts` — аналогично для `message`.
- `src/interceptors/fetch-interceptor.ts`, `xhr-interceptor.ts` / `src/analysis/response-analyzer.ts`
  — решить (не молча оставлять как есть): либо повторно проверять `ctx.isActive` перед записью
  ответа, либо явно задокументировать, что уже отправленный запрос всегда дописывается (осознанный
  trade-off, а не забытый случай).
- `src/monitors/performance-monitor.ts`, `mutation-monitor.ts` — рассмотреть добавление `isActive`-
  проверки внутри самого колбэка наблюдателя, не полагаясь только на `disconnect()`.
- Документация публичного API (README/JSDoc) — явно описать текущие гарантии `cleanup()`/`stop()`,
  включая LIFO-требование для нескольких инстансов, если оно не будет устранено кодом.

**EXPECTED RESULT.** `stop()` либо становится действительно жёсткой границей (ничего не пишется в
контекст после), либо (если это окажется неоправданно дорого/сложно для отдельных путей) граница
явно и честно задокументирована как "best-effort", чтобы будущий Correlation Engine мог сознательно
на это реагировать (например, через `sessionId`/`sequence` — см. Этап 5).

**NON-GOALS.** Не меняет модель данных (`RequestData`/`EventRecord`/...). Не вводит `sessionId`/
`sequence` — это отдельный, более поздний этап (5), контингентный на решении по Minimal Temporal
Envelope.

**TESTS REQUIRED.** Integration-тест: открыть WebSocket/EventSource, вызвать `cleanup()`, затем
эмулировать входящее сообщение на уже открытом соединении — убедиться, что оно либо не попадает в
`ctx`, либо это поведение явно задокументировано и покрыто тестом как согласованное. Тест на два
параллельных инстанса `ResearchCollector` с восстановлением в неправильном порядке — зафиксировать
текущее поведение явно (regression guard), даже если полное исправление отложено.

**MIGRATION RISKS.** Изменение поведения "что происходит после `cleanup()`" потенциально влияет на
существующие интеграционные тесты, которые могли неявно полагаться на текущее (мягкое) поведение —
нужен полный прогон `tests/` после любого изменения здесь.

**ROLLBACK STRATEGY.** Изменения локализованы внутри существующих interceptors/monitors, не меняют
публичные типы — откат сводится к возврату старых версий этих файлов.

(Playwright/Puppeteer — конкретный выбор не решается в этом плане), дополняющий существующие 17

**AFFECTED COMPONENTS.** Новая директория (например `tests/browser/`), новая dev-зависимость,

**EXPECTED RESULT.** Минимум один сквозной тест, запускающий собранный `dist/research-toolkit.bundle.js`
в реальном браузере (Chromium как минимум) против простой тестовой страницы, подтверждающий базовые
инварианты (`window.research` появляется, перехват fetch работает) — расширяемый плацдарм для
Этапа 4.

**NON-GOALS.** Не переписывает существующие jsdom-тесты. Не требует полного браузерного покрытия
всех 17 текущих кейсов — это отдельная, более поздняя работа при необходимости.

**TESTS REQUIRED.** Сам этот этап и есть добавление тестовой инфраструктуры — критерий готовности:
CI зелёный с новым слоем, включённым в обычный прогон.

**MIGRATION RISKS.** CI становится медленнее и требует браузерного рантайма (headless Chromium и
т.п.) — учитывать во времени сборки. Отсутствие такого рантайма в некоторых CI-окружениях.

**ROLLBACK STRATEGY.** Новый, изолированный слой — откат тривиален (удалить директорию/зависимость),
не затрагивает существующие тесты/сборку.

## Этап 3 — Privacy Threat Model Refinement

**OBJECTIVE.** Закрыть подтверждённые в corrective pass пробелы в текущей redaction-модели `src/`
(`PRIVACY_REVIEW.md` §6, находки K.1-K.13): семь путей данных, где `Sanitizer` не вызывается вообще
(navigation URL, dynamic resource URL, performance resource name, `console.error`-аргументы, export
`meta.url`, текст/стек ошибки), плюс структурные пробелы в самом `Sanitizer` (URL fragment/hash не
трогается; список редактируемых имён не покрывает `code`/`access_token`/`session`/`sessionid`/
`csrf`/`xsrf`/`signature`/`sig`; тело запроса не проходит parse-then-redact по полю, только
whole-string).

**WHY NOW.** Независимо от того, какое направление выберет Correlation-трек (Этапы 4-6), это —
подтверждённые, самостоятельные gaps в уже поддерживаемом `src/`, не гипотетические. Более того:
если будущая Minimal Temporal Envelope (Этап 5) добавит поля вроде "описание DOM-цели" в записи
запросов (см. риск "Privacy of DOM target" в `TARGET_ARCHITECTURE_DRAFT.md` §3), закрывать эти
пробелы нужно **раньше**, чтобы не наследовать их в новую функциональность.

**AFFECTED COMPONENTS.** `src/sanitize/sanitizer.ts` (расширить `REDACTED_QUERY_PARAMS`/
`SENSITIVE_PATTERNS`, добавить обработку `urlObj.hash`), `src/monitors/navigation-monitor.ts`,
`src/interceptors/dom-resource-interceptor.ts`, `src/monitors/performance-monitor.ts`,
`src/monitors/error-monitor.ts`/`src/logging/logger.ts` (дать `Logger` зависимость от `Sanitizer`
или явно решить, что это осознанный trade-off), `src/export/exporter.ts` (`meta.url`).

**EXPECTED RESULT.** Каждый из семи путей данных из §6.1 `PRIVACY_REVIEW.md` либо начинает проходить
через `Sanitizer`, либо решение не делать этого явно задокументировано с обоснованием (не молчаливый
пробел). Расширенный список чувствительных имён покрывает реалистичные OAuth/session/CSRF/signature
случаи.

**NON-GOALS.** Не решает "known limitation" (name-based, не content-based redaction) — это
фундаментальное ограничение подхода, не предмет одного этапа. Не вводит metadata-слой для auth
(`present`/`scheme`/`fingerprint` вместо сырых значений, `PRIVACY_REVIEW.md` §7, п.2) — отдельная,
более крупная работа, если приоритизируется.

**TESTS REQUIRED.** По unit-тесту на каждый из семи путей данных (аналогично существующим тестам
`sanitizer.test.js`) — подтверждающий, что данные теперь проходят/не проходят через `Sanitizer`
согласно принятому решению.

**MIGRATION RISKS.** Расширение `REDACTED_QUERY_PARAMS`/`SENSITIVE_PATTERNS` может неожиданно
замаскировать легитимные, нечувствительные значения, если имя случайно совпадёт (например, поле
`code` может означать код скидки, а не OAuth authorization code) — стоит явно обсудить
false-positive risk самой редакции, симметрично тому, как оценивается false-positive risk корреляции.

**ROLLBACK STRATEGY.** Изменения в `Sanitizer` и местах его вызова — локальны, не меняют публичные
типы данных; откат — вернуть предыдущую версию `sanitizer.ts`/`config.ts`.

## Этап 4 — Post-hoc Correlation Study (read-only, без изменения горячего пути)

**OBJECTIVE.** Проверить гипотезу "последнее квалифицирующее взаимодействие пользователя предсказывает
следующий сетевой запрос" эмпирически, **не меняя** production-код `src/` — используя уже собираемые
(без нового поля `lastInteraction`) DOM-события, запросы и navigation-записи.

**WHY NOW.** Прямой ответ на пересмотренную рекомендацию `TARGET_ARCHITECTURE_DRAFT.md` §3, п.1:
единственный источник "требования" для этого примитива — один скопированный legacy-шаблон
(`CORRELATION_GROUNDWORK.md` §3), который сам никогда не был доведён до работающей реализации и
никогда не проверялся эмпирически. Прежде чем вносить изменения в горячий путь `src/`
(`EventMonitor`, все interceptors), нужно знать, насколько вообще надёжна сама идея — на реальных
страницах, а не в теории.

**МЕТОДИКА (детализация того, что нужно сделать при выполнении этапа — не выполняется сейчас).**
На 2-3 реальных SPA (кандидаты: любая GraphQL-based SPA; страница с классическим REST + пагинацией)
собрать существующими сенсорами (без изменения `src/`) поток DOM-событий, сетевых запросов и
navigation-записей за сессию ручного использования. Сопоставить их **пост-фактум**, вне горячего
пути, тремя разными стратегиями:
- **TTL-based correlation** — тот же принцип, что предполагался в legacy: запрос в течение N мс
  после последнего квалифицирующего события.
- **Same-task correlation** — более широкий сигнал: событие и запрос считаются связанными, если
  происходят в рамках одного "макро-действия" пользователя (например между двумя кликами без
  паузы), а не по жёсткому TTL.
- **Multi-signal correlation** — комбинация TTL с дополнительными признаками (например
  `event.isTrusted`, тип события, совпадение DOM-таргета с семантикой запроса), а не голая
  временная близость.

Вручную разметить causal ground truth (какие запросы **на самом деле** были вызваны каким
взаимодействием, по факту ручного наблюдения за сессией) и сравнить с каждой из трёх стратегий.
Измерить как минимум true positives / false positives / precision для каждой. Отдельно, явно
проверить каждый риск из списка `TARGET_ARCHITECTURE_DRAFT.md` §3 п.1 на реальных данных:
background polling, analytics beacon, double-click, click→submit, keyboard activation,
timer-delayed requests — какие из них реально встречаются и как часто портят точность.

**AFFECTED COMPONENTS.** Новый, изолированный анализ-скрипт/notebook, читающий существующий
`exportData()`-вывод постфактум. **Не трогает** `src/interceptors/*`, `src/monitors/*`,
`src/context.ts` — работает только с уже собираемыми данными.

**EXPECTED RESULT.** Количественная оценка (precision/false-positive rate) для каждой из трёх
стратегий на реальных данных — входной материал для решения Этапа 6 (или отказа от него).

**NON-GOALS.** Не встраивается в `src/` ни в каком виде до завершения анализа. Не решает
navigation→network или timer→network корреляции — фокус только на user action → request, как
единственной связи с конкретным legacy-прецедентом (пусть и не рабочим).

**TESTS REQUIRED.** Сам анализ и есть "тест" гипотезы; формальных unit/integration тестов не
требуется, поскольку код не поставляется в `src/`. Ручная валидация ground truth — обязательное
условие достоверности результата.

**MIGRATION RISKS.** Основной риск — методологический, не технический: 2-3 SPA — небольшая выборка,
результат может не обобщаться на все типы сайтов. Явно фиксировать это ограничение в отчёте по
итогам этапа, не выдавать результат за универсальный.

**ROLLBACK STRATEGY.** Read-only анализ существующих экспортов — нет production-кода для отката.

## Этап 5 — Minimal Temporal Envelope: оценка гипотезы + schema/versioning checkpoint

**OBJECTIVE.** По итогам Этапа 4 (и находок `CORRELATION_GROUNDWORK.md` §10 "Temporal Semantics")
явно решить: нужен ли вообще какой-то временной/причинный "конверт" поверх существующих типов данных
(`TARGET_ARCHITECTURE_DRAFT.md` §1.2, "Minimal Temporal / Correlation Envelope" — sessionId, eventId,
source/kind, wall-clock + monotonic timestamp, sequence, sanitizedPayload, parentId/relatedIds,
confidence, ruleVersion), и если да — зафиксировать его схему и версионирование **до** написания
production-кода.

**WHY NOW.** Не раньше — вводить эту инфраструктуру до того, как Этап 4 покажет, что вообще есть
что коррелировать с приемлемой точностью, означало бы проектировать инфраструктуру под
неподтверждённую потребность (тот же аргумент, по которому в первой версии документа был отклонён
Full UEM). Но и не позже — если Этап 4 покажет положительный результат, начинать писать
production-примитив без предварительно зафиксированной схемы (какие поля, какие типы, как версии
схемы будут уживаться при последующих изменениях) — путь к техническому долгу, а не малым
проверяемым шагам.

**AFFECTED COMPONENTS.** Решение и, при положительном исходе, дизайн-документ схемы — не код.
Если решение "да, нужен" — реализация становится отдельным, отдельно спланированным этапом
(вероятно, следующим после Этапа 6, либо parallel с ним, в зависимости от того, что покажет Этап 4).

**EXPECTED RESULT.** Одно из трёх: (a) конверт не нужен — TTL/sequence-проблема из §10
несущественна на практике (маловероятно по фактам corrective pass, но формально возможно); (b)
нужен полный набор полей, как в гипотезе; (c) нужно подмножество (например только `sequence` и
`sessionId`, без `monotonic`/`confidence`/`ruleVersion` на первом шаге). При любом исходе кроме (a)
— зафиксированная схема с версией (`ruleVersion`/schema version) до перехода к Этапу 6.

**NON-GOALS.** Не реализует Full UEM ни в каком виде. Не меняет существующие `RequestData`/
`EventRecord`/... — конверт (если принят) — sidecar, не замена.

**TESTS REQUIRED.** Н/П для решения как такового; если принято "нужен" — тесты появляются вместе с
реализацией на следующем этапе.

**MIGRATION RISKS.** Тот же риск затягивания, что был отмечен в первой версии документа для UEM:
нужно зафиксировать явный критерий "когда достаточно данных для решения" (по итогам Этапа 4), а не
откладывать бесконечно.

**ROLLBACK STRATEGY.** Н/П — решение, не код.

## Этап 6 — Production correlation primitive (контингентно на Этапах 4-5)

**OBJECTIVE.** Только если Этап 4 показал приемлемую точность для одной из трёх стратегий, и Этап 5
зафиксировал схему (если она нужна) — реализовать выбранную стратегию в горячем пути `src/`, явно
адресуя каждый риск из списка `TARGET_ARCHITECTURE_DRAFT.md` §3 п.1 (temporal coincidence,
background polling, analytics beacon, double-click, click→submit, keyboard activation,
timer-delayed requests, programmatic click, `event.isTrusted`, overwriting previous interaction,
TTL selection, privacy of DOM target).

**WHY NOW.** Не раньше — это единственный этап во всём плане, вносящий изменения в горячий путь
сбора данных на основании гипотезы, а не подтверждённого дефекта; он обязан следовать за
эмпирической валидацией (Этап 4), а не предшествовать ей.

**AFFECTED COMPONENTS.** `src/context.ts` (новое поле/структура, форма — по итогам Этапа 5),
`src/monitors/event-monitor.ts` (запись квалифицирующих взаимодействий — множество событий и признак
`event.isTrusted` определяются по итогам Этапа 4, не заранее), `src/interceptors/fetch-interceptor.ts`/
`xhr-interceptor.ts` (чтение при формировании запроса), `src/types.ts` (новое поле в `RequestData`),
`src/sanitize/sanitizer.ts` (редакция DOM-target описания — см. Этап 3).

**EXPECTED RESULT.** Записи запросов, отправленных вскоре после квалифицирующего взаимодействия,
несут информацию о вероятной причине, с зафиксированной (по Этапу 4) степенью доверия — не
бинарный факт, а `confidence`, если Этап 5 принял такое решение.

**NON-GOALS.** Не решает navigation→network/timer→network — остаются отдельными потенциальными
этапами по той же методике (сначала post-hoc study, затем — если оправдано — production).

**TESTS REQUIRED.** Unit: TTL/эвристика по конфигурации, выбранной на Этапе 4. Integration: сценарии
из риск-списка (double-click, click→submit, programmatic click, timer-delayed request) — каждый как
отдельный тест, подтверждающий, что реализация ведёт себя так, как решено по итогам исследования
(включая случаи, когда правильное поведение — **не** связывать событие с запросом).

**MIGRATION RISKS.** Ложные срабатывания — неустранимый источник шума в любой heuristic-корреляции;
задокументировать как known limitation с конкретными числами из Этапа 4, а не как решённую проблему.

**ROLLBACK STRATEGY.** Поле аддитивно и опционально — откат сводится к удалению нового кода без
влияния на существующие структуры данных или тесты.

## Независимый трек — Memory-pressure backpressure для `BoundedStore`

**OBJECTIVE.** Добавить опциональную реакцию на `performance.memory.usedJSHeapSize` как дополнение
(не замену) к существующему TTL/count-based capping в `BoundedStore`.

**WHY (не привязано к номеру этапа — независимо от Correlation-трека).** Единственная возможность,
подтверждённая **всеми 8 из 8** site-specific legacy-файлов независимо (хотя, как и в случае
`lastInteraction`, это один скопированный шаблон, а не 8 независимых решений — см.
`LEGACY_FINDINGS.md` §2), отсутствующая в `src/`. Может выполняться параллельно с любым из этапов
1-6 — не имеет зависимостей от Correlation-работы. Дополнительный мотив из corrective pass:
`PRIVACY_REVIEW.md`/`INVENTORY_MATRIX.md` показали, что совокупный объём сессии в текущем `src/`
выше, чем предполагает наивное чтение конфигов (per-type event умножение, неограниченный начальный
снимок storage) — heap-based backpressure был бы дополнительной защитой сверху.

**AFFECTED COMPONENTS.** `src/storage/bounded-store.ts` (опциональный heap-check перед/после
`rotate()`), `src/context.ts` (`pruneAll()` может дополнительно вызывать более агрессивную очистку
при высоком heap), `src/config.ts` (новый опциональный порог, по умолчанию — выключен или
консервативен).

**EXPECTED RESULT.** Долгие сессии на память-интенсивных страницах не приводят к деградации вкладки
исследователя сильнее, чем сейчас.

**NON-GOALS.** Не заменяет TTL/count capping. Не реализует "полную очистку всего" по примеру legacy
(слишком грубо) — вместо этого более агрессивная ротация существующих `BoundedStore`.

**TESTS REQUIRED.** Unit: мок `performance.memory`, проверка поведения при превышении порога и при
недоступности API (Firefox/Safari).

**MIGRATION RISKS.** `performance.memory` — нестандартный, Chrome-only API; код должен деградировать
до текущего поведения при его отсутствии.

**ROLLBACK STRATEGY.** Полностью опционально через конфиг.

## Этапы, намеренно не включённые в этот план

- **Profiles / декларативный классификатор** (product/post/tweet/pin и т.д. из legacy site-specific)
  — материала достаточно (`LEGACY_FINDINGS.md` §2), но формат конфигурации не спроектирован и
  заслуживает отдельного RT-этапа.
- **Inference-слой** — почти нет материала для опоры (`TARGET_ARCHITECTURE_DRAFT.md` §1.5);
  преждевременно планировать раньше, чем заработает Correlation.
- **AntiBot observability profile** — уникальные находки (`ANTIBOT_MONITOR.js`: наблюдение за
  таймерами, systematic stack traces, sampled event logging) заслуживают отдельного рассмотрения как
  самостоятельный сенсор/профиль.
- **Privacy metadata-слой для auth** (`PRIVACY_REVIEW.md` §7, п.2, `present`/`scheme`/`fingerprint`
  вместо сырых значений) — обоснованное предложение, крупнее по объёму, чем Этап 3 (который решает
  только текущие узкие gaps); может идти параллельно как самостоятельный этап, если приоритизируется.
- **Реализация Minimal Temporal Envelope** (если Этап 5 решит "да") — намеренно не расписана как
  отдельный этап здесь, поскольку её объём и форма прямо зависят от решения Этапа 5.
