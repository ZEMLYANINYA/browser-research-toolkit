# CORRELATION_GROUNDWORK — существующие correlation primitives

> RT-001. Это основа для будущего Correlation Engine (§13 задания). Каждая находка — с точным
> файлом/функцией/строкой. Классификация: **FACT** / **INFERENCE** / **PROPOSAL**.
> Цель — понять, что из "связывания событий" уже существует, насколько это надёжно, и что из идей
> стоит переносить в будущую архитектуру.

---

## 1. Timestamps

**FACT.** Абсолютно все структуры данных во всём репозитории (current + весь legacy) несут поле
`timestamp: Date.now()` на момент создания записи:
- `src/types.ts` — каждый из `RequestData`, `WebSocketMessage`, `StorageEntry`, `ErrorEntry`,
  `PerformanceEntryData`, `EventRecord`, `BeaconRecord`, `EventSourceMessage`, `NavigationRecord`,
  `MutationDiscoveryRecord` имеет `timestamp`.
- Все 8 site-specific legacy-файлов и оба antibot-файла — то же самое, без исключений.

**INFERENCE.** Timestamp — единственный по-настоящему универсальный correlation primitive во всём
репозитории: он есть везде, всегда заполнен, никогда не бывает "заглушкой" (в отличие от
`lastInteraction`, см. §3). Любая будущая корреляция "по времени" (временные окна, "что произошло
в течение N мс после X") технически возможна уже сейчас — просто ни один модуль не использует
timestamp для сопоставления **между** разнотипными записями (запрос ↔ DOM-событие, навигация ↔
запрос) — только для сортировки/ротации внутри одной коллекции (`BoundedStore.rotate()`,
`src/storage/bounded-store.ts:53-69`).

**PROPOSAL (не реализовывать сейчас).** Само наличие timestamp везде — готовая почва для
временнóй корреляции ("окно N мс") без необходимости добавлять новое поле в существующие структуры.

## 2. Request ID и request↔response связывание

**FACT.** `CollectorContext.generateId()` (`src/context.ts:92-94`) генерирует
`req_${counter}_${Date.now().toString(36)}` — единый ID на весь collector, используется как ключ
`BoundedStore`/`Map` для endpoints, jsonData, websockets, eventSources. Все interceptors
(`fetch-interceptor.ts:36`, `xhr-interceptor.ts:21`, `websocket-interceptor.ts:25`,
`eventsource-interceptor.ts:24`) вызывают `ctx.generateId()` один раз на запрос/соединение и
переносят этот `id` через замыкание в `ResponseAnalyzer`, которая дописывает в ту же запись
`RequestData` (`response-analyzer.ts:8-62`) — это уже рабочая **request→response корреляция внутри
одного объекта**, не требующая поиска по коллекции.

**FACT (legacy, тот же механизм).** `SNIF_ENDPOINT_V2.js:generateId()` (1032-1034) — идентичный
паттерн, тот же формат ID.

**FACT (legacy site-specific, вариант через Map).** 5 из 8 site-specific файлов реализуют тот же
принцип иначе — через отдельный `Map`, ключ — сгенерированный ID, куда interceptor кладёт запись
при отправке, а response-обработчик находит её по тому же ID и дописывает поля:
- `ИНСТА.js:351-356` (fetch), `595-599` (XHR) — GraphQL request/response join.
- `ТИКТОК.js:215-222`, `289-296`, `441-448`, `507-514` — `awemeRequests` Map, request+response merge.
- `ФЕЙСБУК.js` — `addAuthFlow({..., requestId: requestData.id})` (495-501) — тоже id-based, но
  привязывает auth-заголовок к запросу, а не тело ответа.
- `X_COM.js:356-378` (fetch), `640-656` (XHR) — pending-запись ищется по `requestId`/`data.id`,
  дописываются `responseSize`/`duration`/`success`/`createdTweetId`.
- `РЕДДИТ.js` — частично, через `postData`/`commentData`, не универсально по всем типам запросов.

**INFERENCE.** Это два независимо изобретённых, но эквивалентных по цели решения одной и той же
задачи (request↔response join через общий id) — current toolkit решает её через замыкание над одним
объектом (эффективнее, без повторного поиска), legacy site-specific — через явный `Map.get(id)`
на стороне обработчика ответа (более гибко для разнесённых во времени/модулях интерсепторов, но
дороже). Обе версии — рабочие, не сломанные.

## 3. `domTrigger` / `lastInteraction` — заявленная, но нереализованная user action → request корреляция

**Это главная находка RT-001 в части корреляции.**

**FACT.** Во всех 8 файлах `legacy/site-specific/*` объект состояния содержит поле
`dom.lastInteraction` (или эквивалент внутри `securityAnalysis.dom`), которое:
1. Объявлено в начальном состоянии (обычно `null` или отсутствует явно, но упоминается в схеме).
2. **Читается** при формировании каждого исходящего fetch/XHR-запроса и записывается в
   `requestData.domTrigger`:
   - `АМАЗОН.js:166` (fetch), `473` (XHR)
   - `ИНСТА.js:178` (fetch), `472` (XHR)
   - `РЕДДИТ.js:192` (fetch), `605` (XHR)
   - `ТИКТОК.js:152` (fetch), `390` (XHR)
   - `ФЕЙСБУК.js:137` (fetch), `339` (XHR)
   - `X_COM.js:178` (fetch), `516` (XHR)
   - `allegro.js:194` (fetch), `679` (XHR)
   - `PINTEREST.js:194` (fetch), `663` (XHR)
3. **Ни в одном из 8 файлов не присваивается** — нет ни одного глобального слушателя
   `click`/`mousedown`/`submit`, который бы писал в `dom.lastInteraction`. Поле объявлено (или
   подразумевается схемой состояния), читается восемь раз в каждом файле, но никогда не
   записывается ни разу.

**FACT.** `legacy/generic/SNIF_ENDPOINT_V2.js` этого поля не содержит вообще — это подтверждает,
что идея возникла и развивалась именно в site-specific ветке, не в общем ядре.

**FACT.** `src/` (current toolkit) не содержит ни `domTrigger`, ни `lastInteraction`, ни любого
эквивалента — `EventMonitor` и все interceptors в `src/` полностью независимы друг от друга и не
обмениваются информацией о "последнем действии пользователя".

**FACT (пересмотрено в corrective pass — важное уточнение доказательной базы).** Независимый review
поставил под сомнение формулировку "восемь независимых подтверждений требования". Проверка
подтвердила его правоту: все 8 файлов — не восемь по-разному спроектированных коллекторов, а один
скопированный шаблон с точечными заменами под площадку. Прямые доказательства (построчное сравнение
всех 8 файлов, см. `LEGACY_FINDINGS.md` §2): идентичное имя переменной состояния
(`securityAnalysis`) и идентичный порядок 5 namespace'ов; идентичный `CONFIG.autoStopMinutes = 30`
и посимвольно идентичный код таймера авто-остановки во всех 8; идентичный порог memory-pressure
`500 * 1048576` во всех 8; идентичные имена и тела helper-методов (`addRequest`, `addWebSocket`,
`addDOMEvent`, ...); идентичная форма объекта `requestData` и идентичное выражение генерации ID;
идентичный стиль русскоязычных комментариев. Вероятность независимого схождения 8 авторов на всех
этих деталях пренебрежимо мала.

**Практический вывод.** Правильная формулировка — "**одно архитектурное намерение, реплицированное
копипастой в 8 производных коллекторах**", а не "8 независимых evidence points". Это меняет вес
находки как статистического аргумента (это n=1 источник дизайна, а не n=8), но **не** меняет её
качественную ценность как сигнала требования: кто-то один явно спроектировал место под эту связь
(поле в состоянии, чтение на каждом запросе) и не довёл до реализации механизм её заполнения —
это по-прежнему реальный, задокументированный в коде замысел, просто с одним, а не восемью
независимыми источниками. Нужен был бы глобальный capture-фазный слушатель на document, записывающий
`{type, target, timestamp}` при каждом квалифицирующем жесте (обычно click/submit/keydown) с TTL
в несколько сотен миллисекунд — но сам факт, что этот замысел не был доведён до конца даже единожды,
не даёт эмпирической информации о том, надёжна ли такая связь на практике (см. §10 ниже и риски
в `MIGRATION_PLAN.md` — прежде чем реализовывать этот примитив в production, стоит валидировать
гипотезу post-hoc, а не полагаться только на то, что кто-то когда-то счёл её нужной).

**PROPOSAL (не реализовывать сейчас, только зафиксировать вывод).** Это ровно тот тип связи, который
нужен для примера из §5 задания ("USER CLICK → DOM EVENT → ... → GRAPHQL REQUEST"). Но, в свете
пересмотра выше, "один задокументированный замысел" — более слабое основание для немедленной
production-реализации, чем казалось изначально. См. `TARGET_ARCHITECTURE_DRAFT.md` §5 и
`MIGRATION_PLAN.md` — рекомендуется сначала post-hoc исследование на реальных SPA, а не прямая
реализация в горячем пути.

## 4. User action → entity корреляции: ancestor-walk (Amazon) и closure-capture (4 других файла)

**Раздел существенно пересмотрен в corrective pass.** Исходная версия называла `findClosestASIN`
"единственной рабочей user action → entity корреляцией во всём репозитории". Независимый review
поставил это под сомнение с двух сторон, и обе подтвердились проверкой кода.

### 4.1 Amazon: алгоритм валиден, но файл в текущем состоянии не исполняется

**FACT.** `legacy/site-specific/АМАЗОН.js:766-774`, функция `findClosestASIN(element)`: при клике
на кнопку "Add to Cart" код поднимается по цепочке `element.parentElement`, пока не найдёт узел с
атрибутом `data-asin`, и логирует синтетическую cart-операцию `click_${Date.now()}`,
привязанную к найденному ASIN (744-754).

**FACT (найдено в corrective pass).** `АМАЗОН.js` целиком не проходит `node --check`: на строке 679
(внутри `analyzeAmazonCookies`) — `SyntaxError: Invalid left-hand side in assignment`, из-за
неверно расположенного `/` в `cookieHeader.match/(session-id=([^;]+)/)` (парсер читает это как
деление, а не как вызов `.match(/regex/)`; подробности — `LEGACY_FINDINGS.md` §2.1). Поскольку весь
файл — один top-level IIFE, эта ошибка блокирует парсинг **всего файла**, включая `findClosestASIN` —
не только в Node, но и в любом браузере, независимо от того, достижима ли ветка с cookie в рантайме.

**Вывод.** Сам алгоритм `findClosestASIN` — синтаксически корректен в изоляции (проверено:
извлечён в отдельный файл, `node --check` проходит чисто) и является хорошо спроектированным
**валидным статическим паттерном** ("подняться по DOM до ближайшего предка с атрибутом X",
атрибут — конфигурируем). Но **как часть коммита `АМАЗОН.js` в его текущем состоянии он не
исполняется вообще** — файл не парсится. Называть его "рабочей корреляцией" было неточно; корректно
говорить о нём как о **валидной идее, не имеющей текущего рабочего воплощения в этом репозитории**.

### 4.2 Четыре других файла: своя, отдельная, реально рабочая closure-based корреляция

**FACT (найдено в corrective pass — не было в исходной версии документа).** Помимо (неисполняемого)
ancestor-walk у Amazon, ещё четыре legacy site-specific файла — все синтаксически корректные,
`node --check` проходит чисто — реализуют свою собственную, структурно более простую, но реально
**исполняющуюся** click→entity корреляцию:

- `РЕДДИТ.js:863-997` (`setupPostElementMonitoring`/аналог для комментариев) — `postId`/`commentId`
  резолвится с контейнера через `MutationObserver` один раз при обнаружении (`getAttribute('id') ||
  getAttribute('data-fullname') || generatePostId()`, 878-880), захватывается в closure; клик по
  upvote/downvote/comments/share/save-кнопке внутри контейнера логирует closure-ID синхронно
  (901-983).
- `X_COM.js:773-867` (`setupTweetElementMonitoring`) — `tweetId` резолвится аналогично
  (`data-tweet-id` или `generateTweetId()`-fallback, 788-790, 874-876), закрывается на like/retweet/
  reply/share-кнопках (810-833).
- `PINTEREST.js:944-1108` (`interactionHandlers`-карта) — `pinId`/`boardId` резолвятся с контейнера
  (`data-pin-id`/`data-test-pin-id` или `generatePinId()`-fallback, 961-963), закрываются на
  save/like/share/comment/closeup-кнопках (976-1007, 1034-1044).
- `allegro.js:944-1093` (`setupProductElementMonitoring`) — `productId`/`auctionId` резолвятся
  аналогично (965-967, 1073), закрываются на view/add_to_cart/add_to_favorites/buy_now/bid-кнопках
  (988-1022, 1079-1086).

**Механизм отличается от Amazon структурно**: это не подъём по DOM в момент клика, а "прочитать
идентифицирующий атрибут контейнера **один раз** при его обнаружении MutationObserver'ом, замкнуть
значение в closure, использовать замкнутое значение при любом клике внутри контейнера" — дешевле
(нет обхода дерева на каждый клик), но зависит от того, что контейнер не переиспользуется под другую
сущность без повторного обнаружения (иначе closure устареет).

**Уточнённый вывод (замена исходного).** Amazon не единственный и не работающий пример user
action → entity корреляции в legacy — он единственный пример конкретно **ancestor-walk**-механизма
(хорошо спроектированного, но сейчас неисполняемого из-за постороннего синтаксического дефекта).
Ещё 4 из 8 файлов (Reddit, X_COM, Pinterest, allegro) реализуют свой, closure-based, реально
рабочий механизм той же задачи. Оба механизма — валидные, обобщаемые идеи для будущего
Correlation/Profile слоя, независимо от какого-либо конкретного сайта: "найти ближайшего предка с
атрибутом X" (ancestor-walk) и "запомнить атрибут контейнера при обнаружении, использовать при
любом дочернем клике" (closure-capture) — два разных, взаимодополняющих паттерна, не конкурирующие
варианта одного и того же.

**PROPOSAL.** Оба механизма — кандидаты для generic-примитива в будущем Correlation/Profile слое,
независимо от какого-либо конкретного сайта из восьми.

## 5. Response → request enrichment (сущность из ответа дописывается в исходный запрос)

**Раздел понижен в classification по итогам corrective pass** — исходная версия называла это
"рабочей" корреляцией; проверка control flow показала подтверждённый риск false positive.

**FACT.** `РЕДДИТ.js:400-414` — regex `"id":\s*"t3_([a-z0-9]+)"` извлекает ID из тела ответа и
дописывает его как `postData.createdPostId` в запись запроса. `X_COM.js:365-379` — тот же паттерн,
regex `"rest_id":"(\d+)"` → `tweetData.createdTweetId`.

**FACT (найдено в corrective pass — ключевое уточнение).** В обоих файлах эта запись **не gated**
условием "запрос был именно создающей операцией". Она выполняется для любого ответа, чей запрос
прошёл широкий классификатор (Reddit: `isPostAPI`, строки 206-207, матчит и `/api/submit`
(create), и `/api/info`/`/comments/` (view/info); X_COM: `isTweetAPI`, строки 191-192, матчит и
`CreateTweet`, и `TweetDetail` (view)). Оба файла отдельно и корректно вычисляют тип операции
(`extractPostInfo`/`extractTweetInfo`, `type: 'create'|'view'|...`), но код записи
`createdPostId`/`createdTweetId` эту классификацию не читает — гейта `if (type === 'create')` нет
ни в одном из двух файлов.

**Конкретный сценарий false positive.** Reddit: `/api/info` по конструкции ищет существующие вещи
по `t3_`-fullname — просмотр существующего поста правдоподобно вернёт `"id":"t3_xxxxx"` в ответе и
ошибочно пометит существующий пост как "созданный". X_COM: `rest_id` — общее внутреннее поле ID для
любого объекта результата GraphQL (Tweet/User/...), присутствует практически в каждом ответе,
включая `TweetDetail` для уже существующего твита — это почти гарантированный false positive при
простом просмотре чужого твита, не только при лайке/ретвите.

**INFERENCE.** Это third отдельный (от §2 и §4) тип корреляции: не запрос↔ответ вообще, а
конкретно "сущность, о которой сообщил ответ, привязывается обратно к запросу". Это уже часть
семантического слоя — ближе к будущему **INFER**, чем к **CORRELATE** в терминах конвейера §5
задания. Реализовано только в 2 из 8 site-specific файлов, оба раза — узким, негейтованным regex,
без обобщённого механизма "сопоставь тело ответа с паттерном, но сначала провалидируй, что операция
действительно создающая, прежде чем вписывать результат как \"created\"".

**Уточнённая классификация: PARTIAL / эвристическая экстракция с подтверждённым риском false
positive**, а не "рабочая response → request enrichment". Любая будущая реализация этой идеи
обязана проверять тип операции перед присвоением "создано", а не полагаться только на совпадение
формы ответа.

## 6. Stack traces как источник initiator-информации

**FACT.** `legacy/antibot/ANTIBOT_MONITOR.js:37` — каждая запись лога (`log()`) захватывает
`new Error().stack`, если `config.captureStackTraces` включено (по умолчанию — да). Это
единственное место во всём репозитории, где стек вызова прикладывается систематически, ко
всем событиям, а не только к ошибкам.

**FACT.** `src/logging/logger.ts:50-57` (`logError`) захватывает `err?.stack`, но только для
`ErrorEntry` — то есть только когда что-то падает, не для discovery-событий (запросы, DOM-события,
навигация).

**FACT.** `ANTIBOT_MONITOR.js:261-286` (`monitorTimers`) — тоже захватывает `new Error().stack`
при каждом вызове `setTimeout`/`setInterval`, что даёт возможность понять, **откуда** (из какого
участка кода страницы) была запланирована функция — уникальная для всего репозитория "initiator
information" в духе `PerformanceResourceTiming.initiatorType`, но для JS-таймеров, а не сетевых
ресурсов.

**INFERENCE.** Систематический захват стека — дорогая (по производительности) операция, поэтому её
присутствие только в antibot-файле, а не в generic/site-specific или в `src/`, скорее всего осознанный
компромисс: antibot observability нужнее знать "откуда конкретно в коде страницы был инициирован
этот вызов" (полезно для reverse-engineering защитных механизмов), тогда как для site-specific
бизнес-семантики (какой продукт искали, что добавили в корзину) initiator-код обычно не важен.

## 7. Timing / duration

**FACT.** `src/types.ts` — `PerformanceEntryData.duration`/`startTime` (из `PerformanceObserver`),
`RequestData` не хранит явную duration (можно вычислить как `status`-время минус `timestamp`, но
явного поля нет ни в `src/`, ни в generic legacy).

**FACT.** Несколько site-specific файлов явно считают `responseTime`/`duration` вручную:
`АМАЗОН.js` (`Date.now() - startTime` в fetch-обработчике), `X_COM.js` (`duration`, дописывается в
response-enrichment, см. §2), `ТИКТОК.js` (аналогично в aweme response merge).

**INFERENCE.** `src/` полагается на `PerformanceObserver`/`PerformanceResourceTiming` для timing
сетевых запросов (косвенно, через `entry.duration`), а не на явный расчёт `Date.now()`-разницы
внутри interceptor — более точный источник (реальные network timings браузера), но не связанный по
`requestId` с самой записью `RequestData` в `src/context.ts` — то есть в **current toolkit** timing
и request-данные технически существуют в двух параллельных, не связанных между собой коллекциях
(`performanceData` и `networkRequests`/`endpoints`), что является пробелом относительно того, что
несколько legacy-файлов делали вручную (attach duration прямо к записи запроса).

## 9. User interaction relationships — что реально связано, а что нет

Сводка по трём типам "клик/действие → Х", встречающимся в задании (§13):

| Связь | Статус | Источник |
|---|---|---|
| USER ACTION → REQUEST | **EXPERIMENTAL** (задумано в 1 общем шаблоне, реплицированном в 8 файлах; не реализовано ни разу) | `domTrigger`/`lastInteraction`, §3 |
| USER ACTION → ENTITY (не запрос, а идентичность в DOM) | **РАБОТАЕТ** в 4 из 8 файлов (closure-capture: Reddit, X_COM, Pinterest, allegro); у Amazon (ancestor-walk) — валидный алгоритм, но сейчас не исполняется из-за постороннего `SyntaxError` в том же файле | §4 |
| REQUEST → RESPONSE | **РАБОТАЕТ**, и в `src/`, и в 5 из 8 legacy site-specific | §2 |
| REQUEST → DOM CHANGE | **НЕ РЕАЛИЗОВАНО НИГДЕ** | ни один файл не сопоставляет исход запроса с последовавшей мутацией DOM |
| RESPONSE → CREATED ENTITY (обратная запись) | **PARTIAL** — реализовано в 2 из 8 файлов (Reddit, X_COM), но с подтверждённым риском false positive (не gated по типу операции) | §5 |
| NAVIGATION → NETWORK ACTIVITY | **НЕ РЕАЛИЗОВАНО НИГДЕ** (сенсор для навигации есть только в `src/`, связи нет; сам сенсор при этом тоже неполон — см. §11) | §8 |
| TIMER → NETWORK ACTIVITY | **НЕ РЕАЛИЗОВАНО НИГДЕ** (наблюдение за таймерами есть только в antibot, связи с сетью нет) | §6 |

**INFERENCE (итог, пересмотрен в corrective pass).** Из семи типов связей, перечисленных в задании
как ожидаемые "частичные связи" (§13), реально и надёжно работает request↔response (в нескольких
независимых реализациях). User-click→entity работает шире, чем считалось изначально — в 4 из 8
файлов, а не в 1. Response→created-entity работает, но с подтверждённым риском false positive, не
"чисто". Все связи, вовлекающие временные окна между разнотипными сенсорами (действие → запрос,
навигация → запрос, таймер → запрос, запрос → DOM-изменение), **не реализованы вообще нигде** — ни
в `src/`, ни в каком-либо из 11 legacy-файлов. Единственное исключение — `domTrigger`/
`lastInteraction`, которое было явно **задумано** (хоть и одним источником дизайна, а не восемью —
см. §3), но не реализовано технически ни разу.

**PROPOSAL (для `TARGET_ARCHITECTURE_DRAFT.md`, не реализовывать здесь).** Это прямо отвечает на
вопрос §16 задания "действительно ли Unified Event Model является необходимым фундаментом для
Correlation": до тех пор, пока нет ни одного связывающего механизма между разнотипными сенсорами
(кроме одного, работающего в рамках одного домена), само существование общей событийной модели не
даёт корреляции бесплатно — модель должна сопровождаться явным слоем сопоставления (временны́е окна,
"последнее квалифицирующее действие", response-entity extraction), которого пока нет в виде
переиспользуемого кода нигде в репозитории.

## 10. Временная модель (temporal semantics) — новый раздел, corrective pass

> Добавлено по итогам независимого review: единая причинная временная линия ("что произошло раньше")
> сейчас затруднена сразу несколькими факторами, ниже — каждый с точным местом в коде.

**FACT.** `Date.now()` — единственный источник timestamp во всём `src/` (32 места вызова,
подтверждено grep по всем модулям: `context.ts`, `collector.ts`, `export/exporter.ts`,
`storage/bounded-store.ts`, `analysis/response-analyzer.ts`, `logging/logger.ts`,
`monitors/storage-monitor.ts`, все 6 interceptors, `monitors/performance-monitor.ts`,
`monitors/navigation-monitor.ts`, `monitors/mutation-monitor.ts`, `monitors/event-monitor.ts`).
`performance.now()` (монотонный, суб-миллисекундный таймер) **нигде не используется** как источник
timestamp записи. Единственное исключение — `performance-monitor.ts:19-25,46-52` копирует
`entry.startTime`/`entry.duration` из самого `PerformanceEntry`, но собственное поле `timestamp`
записи всё равно ставится через `Date.now()` (строки 24, 51) — то есть даже здесь монотонный
источник существует у браузера "под рукой", но не используется для метки самой записи.

**FACT.** Монотонного sequence-номера (счётчика порядка событий, независимого от значения времени)
нет нигде в `src/`, кроме `requestIdCounter` (`context.ts:56`), который используется **только** для
генерации ID запросов (fetch/XHR/WebSocket/EventSource) через `generateId()` — не для DOM-событий,
не для навигации, не для мутаций, не для beacon'ов. `EventRecord`, `NavigationRecord`,
`MutationDiscoveryRecord`, `BeaconRecord` (`src/types.ts:117-122, 155-160, 162-166, 124-128`) несут
только `timestamp`, без поля порядка/последовательности.

**FACT.** В `src/` нет концепции session ID вообще. Единственное совпадение по имени —
`VOLATILE_PARAMS` в `src/analysis/request-fingerprint.ts:8-19` содержит строки `'sessionid'`/
`'session_id'`, но это список **чужих** query-параметров, исключаемых при вычислении fingerprint
запроса (то есть про идентичность сессии **сайта**, а не про идентичность собственного запуска
коллектора). Ни `CollectorContext`, ни `ResearchCollector` не генерируют и не хранят собственный
run/session identifier — в отличие от `legacy/antibot/ANTIBOT_MONITOR.js:19,24-26`
(`generateSessionId()`), которая штампует свой `sessionId` на каждую запись лога.

**FACT (конкретный сценарий столкновения меток времени, продемонстрирован на реальном коде).**
`EventMonitor` регистрирует слушатели на capture-фазе (`document.addEventListener(type, handler,
true)`, `event-monitor.ts:117`), и обработчик синхронно вызывает `ctx.recordEvent(type, record)`
(строка 104) с `timestamp: Date.now()` (строка 100). `FetchInterceptor` оборачивает `window.fetch`
как `async function` (`fetch-interceptor.ts:19`) — по семантике JS тело `async function` выполняется
синхронно вплоть до первого `await` (здесь это строка 52); всё до этого, включая
`timestamp: Date.now()` (строка 43) и `ctx.recordRequest(requestData)` (строка 48), выполняется
синхронно в момент вызова `fetch()`. Если обработчик клика синхронно вызывает `fetch()` (частый
паттерн — "клик по кнопке → немедленный запрос"), обе записи (клик и запрос) получают метку времени
от независимых вызовов `Date.now()` в одном синхронном такте — при разрешении `Date.now()` around
~1мс это может дать **идентичное** значение для обеих записей. Никакого другого поля для разрешения
порядка нет: `EventRecord` не несёт `id`, а `id` у `RequestData` — из независимого счётчика, не
связанного с порядком событий вообще.

**INFERENCE.** Совокупность фактов выше означает: "восстановить, что произошло раньше — клик или
запрос" при совпадении миллисекунды **невозможно** по хранимым данным в их нынешнем виде — не
"сложно", а буквально нет никакой информации, которая позволила бы это сделать. Это прямо
релевантно любому будущему Correlation Engine: временные окна ("запрос в течение N мс после X")
работают только в среднем случае, но не дают строгой причинности при коллизии меток, и у системы
нет способа даже **обнаружить**, что коллизия произошла (нет sequence-номера, который бы это
выявил).

**PROPOSAL (не реализовывать в RT-001).** Минимальный набор изменений, устраняющий эту
неопределённость, не требует Unified Event Model: (1) добавить монотонный sequence-счётчик,
инкрементируемый при каждой записи любого типа (не только запросов), (2) опционально сохранять
`performance.now()` наряду с `Date.now()`, (3) ввести один session ID на инстанс `CollectorContext`.
Это ровно тот состав полей, который в `TARGET_ARCHITECTURE_DRAFT.md` рассматривается как
"MINIMAL TEMPORAL / CORRELATION ENVELOPE" — самостоятельная, более дешёвая альтернатива полному UEM.

## 11. Session / Lifecycle Boundary Integrity — связь с корреляцией

> Полный разбор — `TARGET_ARCHITECTURE_DRAFT.md` (новый раздел, corrective pass). Здесь — почему
> это релевантно именно для Correlation Engine.

**FACT (сводка, подробности — в целевой архитектуре).** `stop()`/`cleanup()` в `src/collector.ts`
не является атомарной границей: WebSocket/EventSource слушатели, уже привязанные к открытым на
момент `cleanup()` соединениям, продолжают писать в `ctx` без проверки `ctx.isActive`; уже
запущенные fetch/XHR запросы дописывают свой ответ в контекст после `stop()`, потому что проверка
активности выполняется только один раз, в момент отправки, а не при получении ответа.

**INFERENCE (почему это важно именно для корреляции).** Если будущий Correlation Engine будет
опираться на понятие "сессии" (например, "все события между `start()` и `stop()` считать одной
логической единицей причинности"), то без исправления этой границы в набор "принадлежащих сессии"
записей будут попадать события, физически произошедшие **после** того, как пользователь считал
сессию завершённой — WS-сообщение, пришедшее через минуту после `stop()`, или ответ на запрос,
отправленный за секунду до `stop()`, но пришедший через 10 секунд после. Скоррелировать такую
запись с "последним взаимодействием" или с "текущей навигацией" на момент её физического прихода
было бы некорректно — она принадлежит уже другому логическому контексту. Это ещё один аргумент в
пользу явного `sequence`/`sessionId` (§10 выше) — они бы, по крайней мере, сделали такие
пост-граничные записи узнаваемыми, а не молча смешивающимися с "настоящими" данными сессии.
