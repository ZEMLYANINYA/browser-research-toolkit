## 1. Текущая redaction-модель (`src/`) — как эталон сравнения

**FACT.** `src/sanitize/sanitizer.ts` — единая точка редакции. Механизмы:
- `sanitizeUrl` — маскирует query-параметры из списка `REDACTED_QUERY_PARAMS`
  (`key`,`token`,`apikey`,`api_key`,`secret`,`auth`,`password`), регистронезависимо (`sanitizer.ts:21-37`).
- `sanitizeHeaders` — маскирует значение заголовка, если **имя** заголовка совпадает с
  `SENSITIVE_PATTERNS.auth`/`.apiKey` (`config.ts:29-35`); остальные заголовки проходят как есть
  (`sanitizer.ts:39-57`).
- `sanitizeBody` — тело auth-эндпоинта (URL содержит `login|auth|register|password`) маскируется
  целиком независимо от содержимого; иначе — whole-string проверка на `containsSensitiveData`, потом
  усечение до 500 симв. (`sanitizer.ts:59-77`). **Уточнение (corrective pass, важно):** независимый
  review указал, что предыдущая версия этого документа ошибочно описывала `sanitizeBody` как
  "parse-then-redact" наравне с ответами. Проверка кода подтвердила ошибку: `sanitizeBody`
  **никогда не вызывает `JSON.parse`** и не редактирует по полю — она только либо маскирует **всё**
  тело целиком (если где-то в сыром тексте нашёлся один из `SENSITIVE_PATTERNS`), либо пропускает
  его как есть с усечением до 500 симв. Parse-then-redact-по-полю применяется **только** к телу
  **ответа** (`ResponseAnalyzer.tryStoreJson` → `sanitizeObject`, `response-analyzer.ts:102-124`) —
  не к телу **запроса**. Оба interceptor'а (`fetch-interceptor.ts:45`, `xhr-interceptor.ts:50`)
  используют именно `sanitizeBody` для тела запроса, то есть без пофлдевой редакции.
- `sanitizeObject` — **parse-then-redact по полю**: рекурсивный обход, каждое поле, чьё **имя**
  (не значение) совпадает с `SENSITIVE_PATTERNS`, маскируется целиком, остальные поля обходятся
  рекурсивно (`sanitizer.ts:79-123`). Это ключевое отличие от всего legacy — маскируется конкретное
  поле, а не весь объект. **Применяется только к телу ответа**, не к телу запроса (см. выше).
- `sanitizeStorageValue`/`sanitizeWebSocketData` — тот же принцип, применённый к
  localStorage/sessionStorage/cookie значениям и WS-сообщениям (`sanitizer.ts:125-147`).
- `containsSensitiveData` (whole-string fallback) используется **только** тогда, когда нет
  структуры для редакции по полю — то есть тело не распарсилось как JSON (`response-analyzer.ts:126-136`).

**FACT.** Redaction включена по умолчанию (`DEFAULT_CONFIG.redactSensitive: true`, `config.ts:13`) —
не opt-in флаг.

**RISK (задокументирован в README, актуален и сейчас).** "Redaction is name-based, not
content-based" — секрет, лежащий в значении под невинным именем ключа (например
`{"data": "<raw token>"}`), не будет пойман ни field-name проверкой, ни whole-text fallback'ом.
Это ограничение относится и к `src/`, и повторяется в §19 `INVENTORY_MATRIX.md` ("sensitive value
detection" → MISSING везде).

## 2. Что собирал generic legacy-скрипт (`SNIF_ENDPOINT_V2.js`)

**FACT.** Тот же набор механизмов, что в `src/` (это его прямой источник — см. `PROJECT_MAP.md`), но
с двумя существенными регрессиями:
1. **Redact-then-maybe-parse**, а не parse-then-redact: `containsSensitiveData(body)` проверяется
   **до** попытки `JSON.parse` (335-364) — при совпадении по любому слову (например "phone" в
   контактных данных бизнеса) блэкаутится **весь** ответ целиком, теряя все остальные поля. README
   `src/` явно фиксирует реальный кейс: это стирало самый полезный endpoint сессии (Google Maps
   place-details) целиком из-за слова "phone" где-то в структуре.
2. **Query-param редакция регистрозависима** (787-791) — `apiKey`/`API_KEY` не совпадают со
   списком `['key','token','apikey',...]`, пропускаются нередактированными.

**RISK.** Оба пункта — это не гипотетические, а подтверждённые (README explicitly documents them
as bugs found via real capture) утечки в предшественнике current toolkit. Это значит: если
когда-либо решат "просто взять что-то полезное из generic legacy напрямую" — редакционный код
брать нельзя, он хуже уже существующего в `src/`.

## 3. Что собирали site-specific legacy-прототипы

**FACT (сквозной паттерн, все 8 файлов).** Ни один из восьми site-specific прототипов не реализует
field-name-based redaction, сравнимую с `Sanitizer`. Вместо редакции используются два других
механизма:
- **Усечение по длине** (`substring(0, N)`, обычно 100-200 символов для токенов/заголовков,
  10 КБ для тел, 50 КБ для GraphQL) — это ограничивает объём хранимых данных, но **не скрывает**
  содержимое усечённой части.
- **Base64-кодирование** тел запросов/ответов (GraphQL, product/aweme/pin API) — это способ
  безопасно хранить бинарно-небезопасные данные как строку, **не** механизм приватности. Полное
  содержимое остаётся восстановимым тривиальным `atob()`.

**FACT (что именно извлекается и хранится "как есть", без маскирования).** Сводно по всем 8 файлам
(точные строки — в `LEGACY_FINDINGS.md` §2):

| Данные | Где хранится | Файлы (пример) |
|---|---|---|
| CSRF-токен | `security.csrfTokens`/`session.csrfToken` | ИНСТА, РЕДДИТ, X_COM, allegro, PINTEREST |
| Bearer/access-токен (усечён до 50-200 симв., не маскирован) | `security.authFlows`/`session.tokens` | все 8, кроме случаев, где путь мёртв (АМАЗОН) |
| Session ID / user ID из cookie | `session.*` (`sessionid`, `ds_user_id`, `twid`, `loid`, `visitor_id`, `customer-id`) | все 8 |
| Auth-заголовки целиком (значение, не только факт наличия) | `security.authFlows`/`*AuthHeaders` | все 8 |
| Полные тела запросов/ответов (до 10-50 КБ, base64) | `network.*` Map-коллекции | все 8 |
| Order/checkout payload (потенциально адрес, состав заказа) | `network.orderRequests` | только `allegro.js` |

**INFERENCE (зачем это было нужно исследователю).** Судя по составу собираемых полей (именно auth/
session/CSRF, а не произвольные данные), цель site-specific прототипов — не просто "что делает
сайт", а конкретно **как сайт аутентифицирует и идентифицирует сессию** (какие заголовки, какие
cookie, в каком формате). Это типичная задача frontend security research (например: "какой у этого
API auth-механизм", "меняется ли CSRF-токен между запросами", "что именно передаётся при логине") —
то есть сохранение auth-данных как есть было не побочным эффектом небрежности, а **прямым
назначением** этих полей в контексте, для которого они писались.

**RISK.** Однако это прямо противоречит "redaction first" философии, к которой уже пришёл `src/`.
Если auth-наблюдение — легитимная исследовательская задача (см. вывод выше), то будущая система
не может просто скопировать этот подход как есть ("хранить всё в открытом виде") — ей нужен способ
удовлетворить обе задачи одновременно: видеть **факт и форму** auth-механизма (какие заголовки
присутствуют, какой scheme, меняется ли токен между запросами), не обязательно сохраняя **сами
значения**. Это именно то разграничение, которое задание описывает в §12 как "metadata вместо
real values" (`present=true`, `scheme=Bearer`, `fingerprint=...`).

**RISK (order/checkout, `allegro.js`).** Единственный legacy-файл, работающий с данными оформления
заказа — потенциально самый чувствительный по составу (адрес доставки, состав корзины, возможно
частичные платёжные данные), при этом с той же "нулевой" редакцией, что и остальные поля.

## 4. Что собирал `ANTIBOT_MONITOR.js` — иной класс данных

**FACT.** `exportLogs()` (`ANTIBOT_MONITOR.js:94-105`) включает `navigator.platform` и
`Array.from(navigator.plugins || []).map(p => p.name)` — список установленных плагинов браузера.

**INFERENCE.** Это данные **о наблюдателе** (fingerprint собственного браузера того, кто запустил
скрипт), а не данные **о сайте** (в отличие от auth-токенов в site-specific файлах). Формально это
не персональные данные третьих лиц — это самоописание среды исполнения. Тем не менее это тот же
класс информации, который anti-bot системы обычно используют для построения browser fingerprint —
собирать его "для наблюдения за тем, как эти системы работают" методологически осмысленно (наблюдать
за собственным fingerprint-профилем, чтобы понимать, что видит защитная система), но стоит явно
отделять от auth/session данных сайта в будущей модели данных: это разные категории с разными
причинами существования.

**FACT.** Двойная персистентность — `localStorage.setItem('antibot_monitor_logs', ...)`
(`ANTIBOT_MONITOR.js:87-88`) — сохраняет собранные логи (включая стеки вызовов, потенциально
содержащие пути к внутренним переменным/токенам, если они встретились в отслеживаемых вызовах)
**на диск браузера**, переживая перезагрузку страницы. Ни один другой файл в репозитории (ни
legacy, ни `src/`) не делает данные персистентными за пределами одной вкладки/сессии.

**RISK.** Персистентность в `localStorage` — дополнительная поверхность: данные переживают
закрытие вкладки и доступны любому скрипту с тем же origin, включая сам исследуемый сайт (если
ключ `antibot_monitor_logs` случайно коллизирует или сайт сканирует localStorage). Ни один
механизм очистки этого ключа при штатной остановке (`stop`) не описан — только явный
`window.clearAntiBotLogs()`.

## 5. Base64 — частая путаница с "защитой"

**FACT/PROPOSAL (терминологическое уточнение для будущей архитектуры).** Все 8 site-specific
файлов используют `btoa()`/base64 для тел GraphQL/product/aweme запросов. Важно явно
зафиксировать: **это не redaction**. Base64 — обратимое кодирование, не маскирование. Любой, кто
видит base64-строку в экспортированных данных, восстанавливает исходное содержимое одним вызовом
`atob()`. Это стоит явно отличать в документации/коде будущей системы от настоящей редакции
(`[REDACTED]`), чтобы разработчик, читающий будущий код, не принял "закодировано в base64" за
"безопасно хранить".

## 6. Privacy gaps в current toolkit (`src/`)

**Раздел полностью переработан и существенно расширен в corrective pass.** Независимый review
указал, что предыдущая версия документа (4 общих пункта) недооценивала масштаб проблемы в самом
`src/` — не только в legacy. Проведён построчный аудит по трём независимым осям для каждого
потенциально чувствительного пути данных: **CAPTURE** (наблюдается ли), **STORE** (хранится ли в
памяти в незамаскированном виде), **EXPORT** (доходит ли до публичного API/экспорта незамаскированным).
Ниже — полный перечень, каждый пункт с точным местом в коде.

### 6.1 Пути, где санитайзер вообще не вызывается — данные хранятся и экспортируются как есть

| Путь данных | CAPTURE | STORE (raw?) | EXPORT (raw?) | Место в коде |
|---|---|---|---|---|
| Navigation from/to URL | ДА | ДА, raw | ДА, raw | `navigation-monitor.ts:53-57` (`record()`) — `sanitizer` ни разу не упоминается в файле; `exporter.ts:50` реэкспортирует как есть |
| URL динамических `<script>`/`<link>` | ДА | ДА, raw | ДА, raw | `dom-resource-interceptor.ts:31,42` (`script.src`/`link.href` напрямую); `exporter.ts:49` |
| Имя ресурса из `PerformanceResourceTiming` (это полный URL) | ДА | ДА, raw | ДА, raw | `performance-monitor.ts:19-25,46-53` (`entry.name`); `exporter.ts:42` |
| Дополнительные аргументы `console.error()` (что угодно, что страница сама туда передала) | ДА | ДА, raw | ДА, raw | `error-monitor.ts:27-30` (`args.slice(1)` без обработки) → `logger.ts:42-58` (`context` сохраняется как есть, `Logger` вообще не имеет зависимости от `Sanitizer`) → `exporter.ts:40` |
| `meta.url` в экспорте (URL страницы на момент экспорта) | ДА | — | ДА, raw | `exporter.ts:30` — `window.location.href` без `sanitizeUrl` |
| Текст ошибки и полный stack trace | ДА | ДА, raw | ДА, raw | `logger.ts:53,56` (`err?.message`, `err?.stack`) — `Logger` не имеет `sanitizer`-зависимости вообще; значение сообщения об ошибке (которое может содержать секрет, если страница сама его туда положила, например `throw new Error('token=' + t)`) становится первой строкой `stack` и тоже не маскируется |

**INFERENCE.** Это не единичные упущения — семь независимых путей данных, ни один из которых ни разу
не обращается к `Sanitizer`. Общая причина видна структурно: `Sanitizer` явно вызывается только в
interceptors, ответственных за сетевые запросы/ответы, и в `StorageMonitor` — но не в
`NavigationMonitor`, `DomResourceInterceptor`, `PerformanceMonitor`, `ErrorMonitor`/`Logger`, и не в
`Exporter` при формировании `meta`.

### 6.2 Пути, где санитайзер вызывается, но покрытие узкое/неполное

| Путь данных | Проблема | Место в коде |
|---|---|---|
| WebSocket/SSE JSON-сообщения | `sanitizeWebSocketData` — только whole-string `containsSensitiveData`, без `JSON.parse` + пофлдевой редакции (в отличие от HTTP-тел ответа) | `sanitizer.ts:138-147` |
| URL fragment/hash | `sanitizeUrl` работает **только** с `urlObj.searchParams` — `urlObj.hash` нигде не упоминается и не трогается вообще; секрет в hash (например OAuth implicit-flow `#access_token=...`) проходит `sanitizeUrl` буквально без изменений | `sanitizer.ts:21-37` (grep на `.hash` в файле — 0 совпадений) |
| Список редактируемых query-параметров — точное совпадение, не паттерн | `REDACTED_QUERY_PARAMS = ['key','token','apikey','api_key','secret','auth','password']`, сравнение — точное совпадение (после lowercase), не substring/regex. Параметры `code` (OAuth authorization code), `access_token`, `session`, `sessionid`, `csrf`, `xsrf`, `signature`, `sig` — ни один из них не входит в список и не редактируется | `sanitizer.ts:4,26-32` |
| `SENSITIVE_PATTERNS` (используется для заголовков/тела/объектов) | Ни одна из 5 категорий (`apiKey`/`auth`/`password`/`credentials`/`cookies`) не содержит подстроки `code` или `signature` — поле/заголовок/параметр с таким именем не попадёт под редакцию нигде, где используется `containsSensitiveData`/`sanitizeObject` | `config.ts:29-35` |

**INFERENCE.** Пункты K.11/K.12 (список редактируемых имён) — структурный gap, компаундирующий все
остальные находки: даже там, где `sanitizeUrl`/`sanitizeObject`/`containsSensitiveData` **вызываются**
(в отличие от §6.1, где они не вызываются вовсе), они всё равно не поймают реалистичные имена
OAuth/session/CSRF/signature-параметров, которых просто нет в жёстко заданных списках.

### 6.3 Пути, где санитайзер применяется корректно — не gap, зафиксировано для полноты

Cookie-значения (`storage-monitor.ts:77`, `sanitizeStorageValue`) и localStorage/sessionStorage
значения (`storage-monitor.ts:33,53`, тот же метод) — оба пути **корректно** проходят через
`sanitizeStorageValue` и на снимке при старте, и при живой записи. Это не regression, а
подтверждение, что остальные пробелы (§6.1-6.2) — не системная неспособность `Sanitizer`
работать, а отсутствие его подключения к конкретным модулям.

### 6.4 Прочие ранее зафиксированные пункты (актуальны без изменений)

1. **Name-based, not content-based redaction** (см. §1) — секрет под неймовым ключом не ловится.
   Актуально и для `src/`, и для любой будущей системы, унаследовавшей тот же подход.
2. **Нет metadata-слоя для auth** — `src/` либо показывает заголовок как есть (не совпало с
   `SENSITIVE_PATTERNS`), либо маскирует его целиком (`[REDACTED]`) — нет промежуточного состояния
   "есть Bearer-токен, вот его схема, вот его fingerprint, но не сам токен". Это именно то, что
   §12 задания предлагает как будущую философию, и именно то, чего одинаково не хватает и `src/`,
   и legacy (просто в legacy эта проблема острее — там нет редакции вообще).
3. **Тело запроса не проходит parse-then-redact вообще** (см. исправление в §1 выше) — `sanitizeBody`
   маскирует весь запрос целиком при совпадении по whole-string паттерну, либо пропускает его как
   есть с усечением; в отличие от тела **ответа**, никакой пофлдевой редакции для тела **запроса**
   нет ни в каком виде.
4. **Нет adaptive/heap-based cap** — `BoundedStore` реагирует только на count/TTL, не на живой
   `performance.memory` (в отличие от всех 8 site-specific legacy-файлов, см.
   `INVENTORY_MATRIX.md`/DATA MANAGEMENT). Это не строго privacy-вопрос, но связано: чем дольше
   живёт сессия без ограничения по факту доступной памяти, тем больше потенциально чувствительных
   данных накапливается в памяти вкладки одновременно.
5. **(Добавлено в corrective pass.) Session/Lifecycle Boundary Integrity влияет и на приватность,
   не только на корреляцию** — см. `TARGET_ARCHITECTURE_DRAFT.md`, новый раздел. `stop()`/
   `cleanup()` не гарантирует немедленного прекращения записи: WebSocket/EventSource-слушатели,
   привязанные к уже открытым на момент вызова соединениям, продолжают писать в контекст без
   проверки активности; уже отправленные fetch/XHR запросы дописывают ответ после `stop()`.
   Практическое следствие для приватности: пользователь, вызвавший `stop()` в расчёте, что сбор
   данных прекратился, может ошибаться — потенциально чувствительные данные из открытых соединений
   продолжают накапливаться в памяти некоторое время после.

## 7. Рекомендуемая будущая философия (PROPOSAL, не реализовывать в RT-001)

Отвечая на пункты §12 задания:

1. **Redaction first остаётся базовым принципом** — `src/` уже на этом построен, менять не за что.
2. **Для auth/session данных — добавить metadata-слой поверх redaction, а не вместо неё.**
   Вместо бинарного выбора "показать как есть / замаскировать целиком": `present: boolean`,
   `scheme: string` (Bearer/Basic/Cookie), `fingerprint: string` (хэш значения, не само значение) —
   удовлетворяет и задаче "видеть механизм аутентификации" (реальная, подтверждённая находкой §3
   потребность site-specific исследователей), и требованию не хранить сырые токены.
3. **Base64 не должен маскироваться под приватность** — если что-то из идеи "полный захват тела
   для GraphQL/бинарных данных" когда-либо будет формализовано, ему тоже нужен explicit
   redact-by-field проход **до** кодирования, а не вместо него.
4. **Данные о наблюдателе (browser fingerprint) — отдельная категория от данных о сайте** (см. §4)
   — не должны попадать в ту же модель редакции/экспорта, что auth-токены исследуемого сайта, у
   них разное назначение и разный уровень чувствительности.
5. **Redaction точка — на границе входа в хранилище**, как уже сделано в `src/`
   (`Sanitizer` вызывается interceptor'ами до `ctx.recordRequest`/`ctx.jsonData.set`) — этот
   принцип уже верен и должен сохраняться в любой будущей архитектуре, а не переноситься "ниже по
   потоку" (например, на экспорт) — иначе данные какое-то время всё равно лежат в памяти
   нередактированными.
